# High-Level System Architecture

## System Overview

BrowserBot is a **local-first AI-assisted browser automation generator** that converts a recorded browser workflow into a validated, installable MCP (Model Context Protocol) tool for Claude Desktop.

The system follows a deterministic pipeline where each stage produces a well-defined artifact consumed by the next stage. Validation gates ensure incorrect or unsafe outputs never progress further.

## Pipeline Orchestrator

### Responsibility

Coordinates the execution of the complete BrowserBot pipeline without implementing business logic.

### Inputs

- User command
- Project configuration
- Pipeline state

### Outputs

- Stage execution status
- Progress information
- Pipeline state

### Responsibilities

- Load project configuration
- Invoke pipeline stages
- Manage execution order
- Record progress
- Handle retries
- Stop execution on failures
- Support future resumable execution

### External Dependencies

- Configuration files
- Logging system

### Failure Modes

- Invalid configuration
- Pipeline interruption
- Unexpected stage failure

# Major Components

## 1. Recorder

### Responsibility

Captures the user's browser interactions while recording a workflow.

### Inputs

- User actions
- Chromium browser session

### Outputs

- `recording.json`

### External Dependencies

- Playwright
- Chromium

### Failure Modes

- Browser launch failure
- Recording interruption
- Unsupported browser action

---

## 2. Action Logger

### Responsibility

Converts raw browser events into a normalized sequence of actions.

### Inputs

- `recording.json`

### Outputs

- `actions.json`

### External Dependencies

- JSON serializer

### Failure Modes

- Invalid event ordering
- Missing browser events
- Corrupted recording

---

## 3. Pattern Extractor

### Responsibility

Uses an LLM to identify:

- Workflow metadata
- User-provided parameters
- Static values
- Dynamic values
- Tool description

### Inputs

- `actions.json`

### Outputs

- `workflow_schema.json`

### External Dependencies

- Ollama (local LLM service, e.g., `llama3.1:8b` for general reasoning)
- LiteLLM abstraction layer (or thin wrapper) for backend-agnostic LLM calls
- Groq free API tier (optional fallback; no credit card required)
- JSON Schema

### Failure Modes

- Invalid JSON
- Incorrect parameter identification
- Hallucinated fields

---

## 4. Parameter Confirmation

### Responsibility

Allows the user to review and approve extracted workflow parameters before code generation.

### Inputs

- `workflow_schema.json`

### Outputs

- `confirmed_schema.json`

### External Dependencies

- CLI or lightweight UI

### Failure Modes

- User rejection
- Missing required parameters
- Invalid edits

---

## 5. Playwright Code Generator

### Responsibility

Generates deterministic Playwright automation using approved templates and workflow metadata.

### Inputs

- `confirmed_schema.json`

### Outputs

- `playwright_script.py`

### External Dependencies

- Ollama (local LLM service, e.g., `qwen2.5-coder:7b` for code generation)
- LiteLLM abstraction layer (or thin wrapper) for backend-agnostic LLM calls
- Groq free API tier (optional fallback; no credit card required)
- Jinja2 templates

### Failure Modes

- Invalid syntax
- Missing imports
- Incorrect locator generation
- Incomplete automation

---

## 6. Validator

### Responsibility

Ensures generated artifacts are safe, valid, and executable before packaging.

Validation includes:

- JSON Schema validation
- AST safety validation
- Runtime execution
- Functional verification

### Inputs

- `playwright_script.py`

### Outputs

- `validation_report.json`

### External Dependencies

- Python AST
- jsonschema
- Playwright
- pytest

### Failure Modes

- Syntax errors
- Unsafe code
- Runtime failures
- Workflow mismatch

---

## 7. MCP Generator

### Responsibility

Generates a FastMCP server exposing the validated browser workflow as a callable MCP tool.

### Inputs

- Validated Playwright script
- Confirmed workflow schema

### Outputs

```text
mcp_server/
```

### External Dependencies

- FastMCP
- Jinja2

### Failure Modes

- Invalid manifest
- Incorrect tool definition
- Packaging errors

---

## 8. Package Generator

### Responsibility

Produces a complete installable MCP package.

### Inputs

```text
mcp_server/
```

### Outputs

```text
installable_package/
```

### External Dependencies

- uv
- pyproject.toml

### Failure Modes

- Dependency resolution failure
- Missing project files
- Invalid package structure

---

## 9. Runtime Executor

### Responsibility

Executes the generated MCP tool when invoked by Claude Desktop.

### Inputs

- User prompt
- MCP package

### Outputs

- Browser execution
- Structured response

### External Dependencies

- Claude Desktop
- FastMCP
- Playwright

### Failure Modes

- Runtime exceptions
- Website changes
- Network timeout
- Authentication failure

## Artifact Metadata

Every artifact produced by the pipeline must include standard metadata to support versioning, traceability, and future schema migrations.

Example:

```json
{
  "schema_version": "1.0",
  "generator_version": "1.0.0",
  "created_at": "2026-07-12T18:30:00Z",
  "artifact_type": "workflow_schema",
  "source": "Pattern Extractor",
  ...
}
```

Standard metadata fields:

- `schema_version`
- `generator_version`
- `created_at`
- `artifact_type`
- `source`
- `checksum` (optional, for integrity verification)

These headers ensure compatibility across future schema revisions while improving debugging and reproducibility.

# Cross-Cutting Concerns

## Local-first Execution

- Browser automation executes locally.
- Workflow recordings remain on the user's machine.
- **Default path (Ollama):** LLM inference runs entirely on the local machine. Zero data leaves the machine at any point in the pipeline.
- **Fallback path (Groq free tier):** Only the scrubbed prompt payload leaves the machine; it never includes raw credentials or PII. Raw browser data never leaves the machine.
- No cloud-hosted browser execution.

---

## Security & Secret Redaction

- Credentials are never persisted.
- Authentication values are replaced with placeholders.
- Sensitive data is excluded from generated artifacts.
- Generated code is restricted through AST validation.

---

## Error Handling

- Every stage validates its input before execution.
- Failures terminate the pipeline immediately.
- Clear diagnostic reports are generated for troubleshooting.
- Recovery occurs only after user correction or regeneration.

---

## Observability & Structured Logging

Every component produces structured JSON logs containing:

- Timestamp
- Component name
- Execution status
- Input artifact
- Output artifact
- LLM backend used (Ollama model tag or Groq model name)
- Retry count (for LLM agent steps)
- Error details (if applicable)

Structured logging enables post-hoc debugging, reliability benchmarking, and audit trail generation without requiring a dedicated observability platform.

---

## Versioning

- Project managed with Git.
- Dependencies locked using `uv.lock`.
- Generated artifacts include metadata describing:
  - BrowserBot version
  - Template version
  - Schema version
  - Generation timestamp

---

## Deterministic Generation

- Template-first code generation.
- Structured JSON contracts.
- Minimal free-form LLM output.
- Human confirmation before generation.
- Repeatable outputs for identical inputs.

---

## Validation Gates

No artifact advances unless validation succeeds.

Validation checkpoints include:

1. Recording integrity
2. JSON Schema validation
3. Parameter confirmation
4. AST validation
5. Runtime execution
6. Functional verification
7. MCP packaging verification

---

## Validation Pipeline

Validation is performed in sequential stages. An artifact proceeds only if the previous stage succeeds.

```text
Playwright Script
        │
        ▼
Schema Validation
        │
        ▼
Security Validation
        │
        ▼
Runtime Validation
        │
        ▼
Functional Validation
        │
        ▼
Validation Report
```

### Validation Stages

**Schema Validation**

- JSON Schema validation
- Required fields
- Artifact integrity

**Security Validation**

- AST allow-list validation
- Unsafe imports
- Restricted APIs
- Secret leakage detection

**Runtime Validation**

- Syntax checking
- Browser launch
- Execution without exceptions

**Functional Validation**

- Expected workflow completion
- Correct parameter substitution
- Expected output verification

# Architectural Principles

## 1. Single Responsibility

Each component performs one clearly defined task and owns one artifact.

---

## 2. Explicit Contracts

Every pipeline stage communicates using structured, versioned artifacts.

---

## 3. Deterministic Generation

Templates define project structure while the LLM contributes only constrained workflow logic.

---

## 4. Validation Before Execution

Artifacts must pass validation before reaching downstream components.

---

## 5. Fail Fast

Errors are detected immediately to prevent cascading failures.

---

## 6. Local-first by Default

Browser execution, storage, validation, and packaging remain on the local machine.

---

## 7. Security by Design

Sensitive information is redacted before persistence, and generated code is restricted through schema and AST validation.

---

## 8. Loose Coupling

Components communicate exclusively through well-defined artifacts rather than direct implementation dependencies.

---

## 9. Reproducibility

A clean environment using the documented setup must reproduce identical project behavior.

---

## 10. MVP-first Design

Architecture is intentionally optimized for:

- One authenticated website
- One deterministic workflow
- One generated MCP tool

Generalization to multiple websites, workflows, and autonomous planning is explicitly deferred until later phases.

---

# Architecture Summary

BrowserBot is designed as a **deterministic, pipeline-oriented architecture** where each stage transforms a single well-defined artifact into the next. Clear component boundaries, explicit contracts, validation gates, and local-first execution minimize coupling, improve reliability, and make the system easier to test, debug, and extend. This architecture provides a stable foundation for incremental implementation while remaining aligned with the project's MVP scope and long-term extensibility goals.


---

# Future Extension Points

The architecture intentionally isolates responsibilities to allow future expansion without redesigning the core pipeline.

Potential extensions include:

- Support for multiple websites
- Multiple recorded workflows
- Additional browser engines (Firefox, WebKit)
- Browser extension–based recording
- Multiple LLM providers (switchable via the existing LiteLLM abstraction layer)
- Frontier hosted model upgrade (e.g., Claude API or GPT-4o) as a quality/speed trade-off, enabled via a one-line config change
- Self-healing selector strategies
- Visual workflow editor
- Cloud-based generation
- Remote execution environments
- Team collaboration and shared workflow repositories
- Enterprise authentication providers
- CI/CD integration for generated MCP tools

These capabilities are intentionally excluded from the MVP but can be introduced by extending existing components rather than modifying their responsibilities.
